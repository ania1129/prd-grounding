# Generation Rules · 生成与引用规则

所有阶段产物和最终 PRD 都必须遵守。违反其中任何一条，视为 PRD 不合格。

## 1. 证据分级

任何关于"现状"的陈述，必须且只能属于以下三类之一：

| 标注 | 含义 | 要求 |
| --- | --- | --- |
| `事实` | 来自代码/文档的直接证据 | 必须带 `path/to/file.ext:LINE` 或 `path/to/dir/` |
| `推断` | 由证据推导出的判断 | 必须写推导依据（引用了哪些事实） |
| `待确认` | 目前无法确认 | 必须写清"缺什么、找谁确认" |

- 没有证据的断言，一律降级为 `推断` 或 `待确认`，不允许装成 `事实`。
- 今天的事实明天可能变：引用记录**版本/分支/提交**（至少记分支名）。

## 2. 引用格式

```text
services/order/src/order.service.ts:142
services/order/src/order.service.ts:142-168
migrations/20260101_add_refund_table.sql
docs/adr/0007-refund-flow.md
```

- 行号用 `:LINE`，区间用 `:START-END`。
- 优先引用**最小且稳定**的锚点：函数/类/迁移文件，其次才是行号。
- 证据索引（PRD 第 16 章）把每个引用映射回它的结论。

## 3. 编号体系

| 编号 | 用于 | 出现位置 |
| --- | --- | --- |
| `F1…Fn` | 功能点 | 02 / 04 / 06 / 07 / 08 / PRD |
| `P1…Pn` | 主流程 | 02 / 07 / 08 / PRD |
| `Q1…Qn` | 待确认点 | 08 / 09 / PRD |
| `方案 A/B/C` | 方案候选 | 05 / 06 |
| `R1…Rn` | 风险 | 02 / 04 / PRD（可选） |

编号一旦分配不得复用或改号；新增只能追加。

## 4. 决策规则

- **方案选定前**：不臆造业务决策；缺口、矛盾、边界先编号为 `Q*`。
- **方案选定后**：阶段 9 对每个 `Q*` 自动决策，依据优先级：
  与现状语义一致 → 最小改动且可回滚 → 不改变数据可见权限 → 采用默认建议 → 风险最低可灰度。
- 不编造业务规则、字段含义、状态取值、指标基线、人名、日期、数据量。
- 不把"行业惯例"写成"需求要求"。
- 真正无法判断的：写成"假设 + 风险 + 验证方式"，保留为残留风险，不阻塞流程。
- 代码与需求矛盾时：两边都记录，给出决策与依据，不擅自抹掉一方。

## 5. 脱敏与安全

- 不粘贴密钥、token、密码、连接串、个人隐私、真实用户数据。
- 引用配置只写"键名 + 用途"，不写值。
- 需要示例时用假数据，并标注"示例"。
- 不在 PRD 中附带大段专有代码；必要时 ≤10 行片段并说明用途。

## 6. 语言与格式

- 语言跟随用户：用户中文则 PRD 中文，术语保留英文原名（如 `OrderService`）。
- Markdown 输出；表格用于对比与清单，避免大段无结构文字。
- 时间用 `YYYY-MM-DD`；金额注明币种与精度；比例注明口径。
- 每个阶段产物顶部写：阶段号、标题、生成/更新时间、关联需求 slug。

## 7. 阶段文件约定

- 文件名见 `SKILL.md` 的"产物与目录"，不得改名。
- 已存在的文件追加/更新，不覆盖 PM 已确认的内容。
- 每个文件末尾保留"待确认"小节，汇总本阶段产生的 Q。
- 每完成一个阶段，更新 `state.json`（用脚本，不手改）。

## 8. 最终 PRD 要求

- 结构以 `assets/prd-template.md` 为准。
- 必需章节（术语表前置）：术语表、背景与目标、用户与场景、目标与提升指标、需求内容、数据验证、权限与安全。
- **最终 PRD 不写**：现状基线、影响面、接口变更、非功能需求、埋点与观测、灰度回滚迁移、
  风险与依赖、决策记录、证据索引、变更记录。这些内容保留在工作区阶段文件（04/07/08/09）
  供研发追溯，不进入给业务/评审看的 PRD。
- 每个功能点 `F*` 在 PRD 中只能出现一次"定义"，其余位置引用编号。
- 语言简洁，面向产品评审；不堆技术细节。
- 逆向流程与异常只写**本次改动**引入或改变的场景，不复述系统原有通用异常。
- 功能点只拆**本次真正变化**的部分；权限/开关类改造通常 1–2 条，不要把既有能力逐条列出。
- 需求内容必须有「产品详细描述」：入口与展示规则、操作流程、权限与数据范围、文案提示、灰度。
- 目标与指标少而准：1 个核心 + 1 个护栏即可，不堆过程指标与长表格。
- PRD 模块固定、全部保留；与本次需求无关的模块直接写 `【本次需求不涉及】`，不要删章节，也不要硬凑内容。
- 默认无灰度：需求未明确要求灰度时，PRD 不写灰度、不设计灰度方案；产品明确提出灰度时，才单独分析（可作为独立小节或独立需求）。
- 生成前先判需求级别：L1 一句话需求只写主流程与受影响处；L2 简单功能迭代写清功能点/入口/流程；L3 大流程需求逐模块详细描述并前后闭环。判不准按低一级写。

## 9. 质量自检（输出前）

- [ ] 所有 `事实` 都能在证据索引里找到。
- [ ] 所有 `F*` 前后一致，无孤儿编号。
- [ ] 所有 `Q*` 在 09 中有决策或"假设 + 风险"。
- [ ] 没有未标注的裸结论。
- [ ] 没有泄露敏感信息。
- [ ] 指标都有公式/来源/基线。
- [ ] 方案 ≥2 且差异真实。
- [ ] 逆向流程覆盖每个主流程。

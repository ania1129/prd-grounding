# Solution Design · 方案、详细设计与逆向流程

阶段 5–7 的写法与检查表。核心要求：**方案给选择，设计给落地，逆向给兜底，待确认给闭环。**

## 一、方案候选（阶段 5）

### 原则

1. **≥2 个方案，且是路线差异**：数据口径不同、架构位置不同、同步/异步不同、
   自研/复用不同、一次性/分阶段不同。不是"全做 vs 少做"。
2. 每个方案都能独立落地，不能是半成品。
3. 明确标注对目标指标的预期贡献——方案是为指标服务的。
4. 给出推荐意见和理由，但**决定权留给 PM**。
5. 方案数量控制在 2–4 个；超过 4 个说明没收敛。

### 方案模板

```markdown
### 方案 A · <一句话命名>

- **核心思路**：
- **改动范围**：涉及模块 / 接口 / 表 / 任务（引用 04 影响面）
- **优点**：
- **缺点 / 风险**：
- **成本粗估**：x 人日（研发 + 测试）
- **对目标指标的预期贡献**：指标 X 预计 +y%（依据/假设）
- **兼容 / 迁移 / 回滚**：
- **不适用场景**：
```

### 对比表模板

| 维度 | 方案 A | 方案 B | 方案 C |
| --- | --- | --- | --- |
| 核心思路 | | | |
| 改动面 | | | |
| 成本（人日） | | | |

### 推荐意见写法

> 推荐方案 B：在现有订单服务内扩展，复用已有退款表结构与状态机，改动面最小、
> 对指标 X 的贡献最直接；代价是暂时不支持跨商户批量退款，可作为二期。
> 最终由产品经理选择。

**禁止**：只给一个方案；把推荐写成"必须"；方案里夹带未确认的业务假设。

## 二、详细设计（阶段 6）

按下面清单逐项写"有 / 无 + 理由"，无理由不允许留空。

### 1. 模块与改动点
- 文件/目录级清单：新增、修改、删除。
- 每个改动点关联功能点 `F*` 与方案。
- 标注 `依据：04#...`（现状驱动）或 `新增设计`。

### 2. 主流程时序
- 步骤、参与方（前端/网关/服务/DB/MQ/第三方）、数据流向。
- 复杂流程用 mermaid `sequenceDiagram` 或 ASCII。
- 同步 vs 异步写清楚；失败点标出来。

### 3. 数据模型变更
- 表 / 字段 / 类型 / 默认值 / 是否可空 / 索引 / 唯一约束。
- 迁移脚本策略：在线 DDL、双写、回填、灰度。
- 向后兼容：老数据、老代码、缓存 key、序列化。

### 4. 接口变更
- 新增/修改的接口：method + path + 幂等性。
- 请求/响应示例；字段必填与校验。
- 错误码与错误结构。
- 版本策略与兼容期。

### 5. 权限与安全
- 新权限点、角色、数据范围。
- 越权校验、审计日志、脱敏。
- 敏感操作二次确认 / 审批。

### 6. 非功能
- 性能：QPS、P99、数据量、批处理窗口。
- 容量：存储增长、清理策略。
- 可用性：降级、限流、熔断。
- 合规：隐私、留存、审计。

### 7. 埋点与观测
- 事件名、触发时机、参数、口径。
- 日志、指标、告警、看板。

### 8. 灰度与回滚
- 开关粒度（全局/租户/用户/比例）。
- 灰度批次与观察指标。
- 回滚触发条件、回滚步骤、数据回滚策略。

### 9. 实施步骤 / 里程碑
- 拆分到可交付的小步；每步可验证。
- 依赖顺序与并行项。

### 10. 测试要点
- 主流程、逆向流程、异常、边界、并发、幂等。
- 回归范围。

## 三、逆向流程与待确认（阶段 7）

### 逆向 / 异常矩阵

| 主流程 | 逆向/异常场景 | 期望行为 | 状态变化 | 待确认 |
| --- | --- | --- | --- | --- |
| P1 发起退款 | 重复提交 | 幂等返回 | 无变化 | Q1 |
| P1 发起退款 | 支付失败 | 回滚订单状态 | 待退款→原状态 | Q2 |

**必须覆盖**：撤销、失败、回退、超时、并发、重复提交、退款、删除、补偿、幂等。

### 状态机全量

| 当前状态 | 事件 | 目标状态 | 校验条件 | 非法迁移处理 |
| --- | --- | --- | --- | --- |

- 状态 × 事件要全覆盖，不能只写正常路径。
- 非法迁移必须定义行为（拒绝 / 告警 / 忽略）。

### 候选待确认清单

每条必须带默认建议，供阶段 9 自动决策：

```markdown
### Q1 · <一句话问题>
- **为什么重要**：
- **影响范围**：F3 / 流程 P2 / 接口 POST /orders/{id}/refund
- **候选答案**：
  - A) ...
  - B) ...
  - C) ...
- **默认建议**：B，理由 ...
```

**禁止**：`Q: 这个怎么处理？` 这种没有候选答案的提问；把已知答案的问题塞进来凑数。

### 自动决策（阶段 9，无需 PM 确认）

方案选定后，技能按固定优先级对每个 `Q*` 给出结论：

1. 与现有代码语义一致（例如 `ownerUid || currentHandlerUid`）；
2. 最小改动、可回滚，不扩大影响面；
3. 不改变数据可见权限、不影响其他角色；
4. 采用阶段 7 给出的默认建议；
5. 风险最低、可灰度验证。

决策记录写入 `09-decision-log.md`：

| Q | 决策 | 依据 | 影响 | 风险 | 复盘 |
| --- | --- | --- | --- | --- | --- |
| Q1 | 幂等键用订单号+退款单号 | 与现有单号规则一致 | 中 | 历史数据无幂等键 | 上线后观察重复率 |
| Q2 | 本期不做 | 二期需求 | 低 | 退款成功率统计暂缺 | 二期补 |

- 真正无法判断的：写成"假设 + 风险 + 验证方式"，保留为残留风险，不阻塞流程。
- 决策一旦写入，最终 PRD 第 14 章直接引用，不再向 PM 二次确认。

# 05 · 解决方案候选（样例）

- 关联需求：`order-partial-refund`
- 前提：阶段 1–4 已完成

## 方案 A · 扩展现有退款单（推荐）

- 核心思路：在现有退款单上加明细表 `order_refund_item`，复用状态机与事件。
- 改动范围：`services/order`、`services/inventory`、`services/finance`、客服前端。
- 优点：改动面小、复用已有事件与审批、交付快。
- 缺点 / 风险：退款单模型变复杂；历史整单退款需兼容。
- 成本粗估：8 人日。
- 对目标指标的预期贡献：售后客诉率预计 -25%（假设）。
- 兼容 / 迁移 / 回滚：新增明细表可空，开关控制；回滚隐藏入口即可。
- 不适用场景：未来要做"跨订单合并退款"。

## 方案 B · 商品子单模型

- 核心思路：为每件商品生成子订单，退款作用于子订单。
- 改动范围：订单主模型、库存、财务、对账。
- 优点：粒度最清晰，扩展性最好。
- 缺点 / 风险：数据迁移大，周期长。
- 成本粗估：20 人日。
- 对目标指标的预期贡献：售后客诉率预计 -30%。
- 兼容 / 迁移 / 回滚：需双写与迁移，回滚成本高。
- 不适用场景：近期要快速上线。

## 方案 C · 接入集团退款中台

- 核心思路：把退款动作交给集团中台，本系统只做编排。
- 改动范围：退款编排、回调、对账。
- 优点：长期可复用。
- 缺点 / 风险：依赖外部排期，不可控。
- 成本粗估：12 人日 + 排期。
- 对目标指标的预期贡献：售后客诉率预计 -18%。
- 兼容 / 迁移 / 回滚：中台灰度能力决定。
- 不适用场景：需要本期独立上线。

## 对比

| 维度 | A | B | C |
| --- | --- | --- | --- |
| 成本（人日） | 8 | 20 | 12+ |
| 风险 | 低 | 中 | 高 |
| 对指标贡献 | -25% | -30% | -18% |
| 交付速度 | 快 | 慢 | 中 |
| 技术债 | 低 | 低 | 低 |
| 推荐度 | ★★★ | ★★ | ★ |

## 推荐

推荐方案 A：复用现有退款单与事件、改动面最小、对客诉率贡献直接；
代价是暂不支持跨订单合并退款。最终由产品经理选择。
